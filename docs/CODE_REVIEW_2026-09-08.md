문제의 중심은 DB 용량이 아니라 **화면 책임 집중, 이중 데이터 연결, 비동기 요청과 캐시의 생명주기 관리**다.

## 2. 실제 구조

```text
React 화면 / App.jsx
  ├─ 사용자·프로젝트 선택, 라우팅, 저장 잠금, 낙관적 수정
  ├─ 메모리 캐시(10분) + 사용자별 sessionStorage 캐시(최대 30분)
  └─ API dataSource → Supabase hybridApi
       ├─ Supabase Auth → read_bootstrap → 현재 탭 RPC
       │    ├─ 업무·간트·이슈: read_task_workspace / mutation RPC
       │    ├─ 통합관리·내부 회의록: read_operations_dashboard
       │    ├─ 실행계획·성과·권한: 개별 Supabase 경로
       │    └─ 계정대장: 메타데이터 RPC / 비밀번호 건별 Vault 열람
       └─ legacy Sheets 세션 → Apps Script
            └─ 남은 콘텐츠·성과추적·세부로그, 기존 overview 등의 호환 경로
```

첫 로그인은 Supabase 직접 인증을 먼저 시도한다. 기존 계정 호환을 위해 실패 유형에 따라 Auth bridge를 이용하며, 직접 로그인 성공 후에도 Sheets 호환 세션을 백그라운드에서 준비한다. 따라서 현재 구조는 완전한 Supabase 단일 백엔드가 아니다.

화면 필터는 로컬 처리하고 업무·간트·진행상황은 업무 리소스를 공유한다. 통합관리는 프로젝트별 요청 반복 대신 집계 RPC 하나를 사용하는 구조다. 이 원칙은 유지했다.

## 6. 운영 DB 진단 — 변경하지 않음

2026-09-08 16:22 KST, 마케팅 프로젝트 `mmvbowojmejhnztajlde` Advisor 결과:

- 보안 WARN 10개: authenticated 호출 가능한 SECURITY DEFINER 함수 9개, 유출 비밀번호 차단 비활성 1개.
- 성능 INFO 28개: 모두 미사용 인덱스. 이번 진단 결과에 다른 종류의 성능 경고는 없었다. 이는 실제 느린 쿼리가 없다는 의미가 아니다.

SECURITY DEFINER 경고는 취약점 확정과 다르다. 현 구조의 RPC는 내부 권한 검사가 필요하며, 이를 일괄 SECURITY INVOKER로 변경하거나 실행 권한을 제거하면 정상 기능이 깨질 수 있다. 로컬 회귀검사는 통과했지만 운영 함수별 최신 정의·권한 검토는 별도로 필요하다. [공식 경고 설명](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

유출 비밀번호 차단은 운영 보안 설정·사용 가능 조건을 확인 후 결정할 항목이다. 임의로 켜거나 기존 비밀번호를 바꾸지 않았다. [공식 비밀번호 보안 안내](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

미사용 인덱스도 새 기능, 데이터량, 통계 초기화 시점에 따라 아직 쓰이지 않았을 수 있다. EXPLAIN과 충분한 관찰 기간 없이 삭제하지 않았다. [공식 인덱스 경고 설명](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).

## 7. 남은 구조적 과제와 우선순위

### 1순위: 관측과 데이터 경계

- 로그인·bootstrap·탭 조회·mutation 각각 소요시간/응답 크기/실패 코드를 기록하고 p50/p95를 분리한다. 비밀번호·세션 토큰·업무 본문은 측정 로그에 넣지 않는다.
- 운영의 실제 병목을 측정한 뒤 API 지연과 화면 렌더링 지연을 구분한다. 이 점검에서는 운영 계정으로 저장하지 않았으므로 실제 저장 p95는 미측정이다.
- 다른 사용자가 수정한 데이터는 현재 사용자 캐시 만료 전까지 보이지 않을 수 있다. 화면 복귀 시 재검증, 제한적 폴링, Realtime 중 갱신 요구에 맞는 방식을 선택한다. 저장 버튼 응답과 전체 프로젝트 재조회는 계속 분리한다.
- 같은 사용자의 역할·공개 범위가 바뀔 때 sessionStorage의 기존 리소스 재사용 정책을 별도로 검증한다. 사용자 ID별 분리만으로 권한 변경까지 완전히 처리했다고 볼 수 없다.

### 2순위: Sheets 의존 제거

- 콘텐츠·성과추적·세부로그·overview·프로젝트 수정 등 실제로 남은 Sheets 경로를 기능별로 목록화하고 Supabase 구현/이전 완료 여부와 대조한다.
- 화면에서 숨겼다고 백엔드 경로가 사라지는 것은 아니다. 사용하지 않는 기능은 명시적으로 중지하고, 필요한 기능만 이전한다.
- 읽기·쓰기·권한·이력 검증 후 legacy 세션과 로그인 bridge를 제거한다. 단순히 URL만 바꾸거나 로그인 fallback부터 끊지 않는다.

### 3순위: 프런트 책임 분리

- 수정 후에도 App.jsx는 3,596줄, 공통 styles.css는 11,717줄이다. 줄 수 자체가 버그는 아니지만 라우팅·표·간트·모달·저장·캐시가 한곳에 있어 변경 영향이 크다.
- 업무 표/간트, 권한관리, 생성·편집 모달, 데이터 캐시·mutation 조정자를 독립 모듈로 순차 분리한다. DOM/CSS 계약을 보존한 상태에서 한 영역씩 테스트한다.
- 공통 CSS를 화면별로 분리하고 덧붙여진 override를 정리한다. 한 번에 전역 스타일을 삭제하지 않는다.
- 대량 업무의 일괄 patch는 현재 행별 목록 순회를 반복한다. 실제 100/500/1,000행 렌더링을 측정한 뒤 단일 패스 갱신과 행 가상화를 적용한다. 간트 드래그·키보드·스크롤·고정 열을 포함한 검증이 선행돼야 한다.
- 소스 문자열 검사만으로는 이번 세션 경합을 잡지 못했다. 사용자 전환, 느린 응답, 두 사용자 동시 수정, 저장 실패/재시도, 모바일 입력 동작 검사를 CI의 독립 회귀검사로 확장한다.

## 8. 운영 반영 전 조건

배포는 아직 하지 않았다. 운영 반영 시 변경분만 묶어서 배포하고 Pocket/NS/고객 각 역할에서 로그인 → 프로젝트 전환 → 업무 수정 → 통합관리 재확인 → 로그아웃 순서의 스모크 검증을 권장한다. DB 마이그레이션은 이번 수정에 필요 없다.

이번에 고친 것은 확인한 결함과 일부 초기 로딩 비용이다. 모든 페이지가 완전히 최적화됐다거나 보안상 문제가 없다고 결론내리지 않는다.
