# 고객 브리핑·운영 관제 화면 기획

기준일: 2026-09-03  
상태: 구현 전 기획안  
목표: 같은 원장 데이터를 고객용 보고와 내부 의사결정이라는 서로 다른 목적에 맞게 보여준다.

단일 파일 화면 시안(로컬 전용): `dashboard-prototype.html`
시안 범위: 고객 브리핑·운영 관제 전환, 회사 선택, 운영 상태 필터. 화면의 수치는 실제 원장과 연결하지 않은 명시적 예시 데이터다.

2026-09-03 시안 수정: 성과·조회·도달 원장이 아직 안정적으로 집계되지 않는 현재 단계에는 고객 브리핑에서 성과 차트를 제외한다. 고객 화면의 우선순위를 `진행된 업무 / 진행 중인 업무 / 진행될 업무 / 고객 확인 요청 / 프로젝트 진행 단계`로 변경하고, 성과 모듈은 실제 집계 시작 후 추가한다.

2026-09-03 데일리 체크 시안 추가: 매일 업무를 확인하는 내부 화면을 `오늘 체크 대상 / 오늘 완료 / 기한 초과 / 고객 회신 대기` 요약, 우선순위·프로젝트·업무·상태·담당·마감·최근 갱신을 포함한 오늘 실행 목록, 오늘 반드시 결론낼 항목, 프로젝트별 체크 결과로 구성한다. 체크 동작은 실제 구현에서 업무 완료 저장과 사람 활동 로그를 동시에 남기며, 고객 브리핑이나 장기 운영 관제와 역할을 섞지 않는다.

## 1. 현재 결정

### 운영 구현: 업무 → 진행사항

- `#tasks/progress`로 고객 브리핑의 네 영역을 실제 업무·회의·이슈 데이터에 연결했다. 내부 운영 관제는 `#portfolio` 통합 관리 메뉴에서 접근 가능한 전체 프로젝트를 Supabase 집계 RPC 1회로 조회하며, 고객 권한에는 노출하지 않는다.
- 업무 권한으로 진입하며 회의록은 별도 기존 권한을 유지한다. 내부 입력만 기존 issue mutation에 연결하고 고객의 쓰기 권한은 변경하지 않았다.
- 답변은 기존 이슈 추가 메모에 누적한다. 독립 댓글 행·수신 알림·고객 직접 답변은 후속 기능이며 구현됐다고 안내하지 않는다.

### 최신 시안: 업무·회의·상호 확인 중심

- 고객 브리핑은 `진행된 업무 / 이번 주 진행 예정 업무 / 지난 회의 내용 / 서로 확인할 콘텐츠·내용` 네 영역으로 구성한다. 진행된 업무는 완료뿐 아니라 실제 진행 상황을 상태 배지와 함께 보여준다.
- 지난 회의는 날짜·참석자·논의·결정·담당별 후속 업무를 표시한다. 실제 연동 시 고객 공개 회의만 사용한다.
- 확인 요청은 포켓·NS·고객 모두 작성하고 대상 조직을 지정한다. 제목·내용·http(s) 링크, 답변, 확인 완료/재요청을 지원한다.
- 단일 HTML의 등록·답변·상태 변경은 메모리 시연만 지원하며 새로고침하면 초기화된다. 실제 저장·인증·배포는 연결하지 않았다. 실서비스의 작성자는 선택값을 신뢰하지 않고 로그인 계정으로 확정해야 한다.
- 다음 단계에서는 기존의 고객 읽기 전용 원칙을 전체 해제하지 않고 확인 요청/답변에만 제한적 쓰기 권한을 추가한다.

- 별도 `일정표` 메뉴는 제거한다. 실제 일정 편집과 간트는 `업무` 화면 안에 유지한다.
- 신규 화면은 `고객 브리핑`과 `운영 관제` 두 개로 분리한다.
- 기존 `총괄 현황`을 그대로 둔 채 비슷한 화면을 두 개 더 붙이지 않는다. 신규 화면 검증 후 `총괄 현황`을 고객 브리핑 또는 운영 관제로 대체해 중복 메뉴를 정리한다.
- 고객용은 프로젝트 하나만 보여주고 기본 읽기 전용으로 둔다. 내부용은 여러 프로젝트를 비교하고 기존 업무·성과 상세 화면으로 이동하게 한다.
- 실제 값이 없거나 연동되지 않은 지표는 `0`이 아니라 `집계 전` 또는 `미연동`으로 표시한다.

## 2. 참고한 구조와 적용 원칙

- Google Analytics 개요 보고서는 주제를 요약 카드로 먼저 보여주고 각 카드를 상세 보고서로 연결한다. 두 화면 모두 `요약 → 원인 확인` 구조를 사용한다.
- GA Reports snapshot은 사용자 행동, 매출, 마케팅 성과 등 목적별 카드 구성을 사용한다. 모든 프로젝트에 같은 장식용 차트를 붙이지 않고 프로젝트별 핵심 KPI만 노출한다.
- Looker Studio의 컨트롤과 스코어카드는 기간·프로젝트·담당·상태 필터와 단일 KPI 비교에 적합하다. 내부 화면 상단 필터와 KPI 카드에 적용한다.
- Asana Portfolio는 프로젝트 건강도, 담당자, 마감, 진행률, 막힘과 업무 부하를 한 화면에서 비교한다. 내부 운영 관제의 핵심 정보 구조로 사용한다.
- HubSpot 대시보드는 자주 쓰는 필터를 상단에 고정한다. 내부 화면의 빠른 필터는 최대 4개로 제한하고 상세 조건은 별도 필터 패널로 보낸다.

## 4. 고객 브리핑

### 사용자가 답을 얻어야 하는 질문

1. 프로젝트가 정상 진행 중인가?
2. 이번 기간에 무엇이 완료됐는가?
3. 다음으로 무엇을 하는가?
4. 고객이 확인하거나 결정할 사항이 있는가?
5. 합의한 KPI는 목표에 가까워지고 있는가?

### 화면 구조

```text
[프로젝트명] [조회 기간] [마지막 갱신] [전체 상태]

[진행률] [완료/전체] [핵심 KPI] [고객 확인 요청]

[이번 기간 요약 --------------------------------] [고객 확인 필요]
[완료한 일 / 현재 하는 일 / 다음 기간 할 일      ] [승인·답변·자료 요청]

[핵심 KPI 1 추이] [핵심 KPI 2 추이] [핵심 KPI 3 추이]

[최근 완료 산출물과 링크 -----------------------] [다가오는 마일스톤]
```

### 표시 규칙

- KPI 카드는 프로젝트에서 `핵심`으로 지정한 최대 4개만 표시한다.
- KPI 실제값이 없으면 `집계 전`, 데이터 소스가 없으면 `미연동`을 표시한다.
- 완료 산출물은 완료 상태이면서 완료 링크가 있는 업무를 우선 표시한다.
- 고객 확인 요청은 미해결 이슈 중 고객 담당 또는 고객 승인 대기인 항목만 표시한다.
- 날짜는 고객의 지역 시간대 기준이며, 마지막 갱신 시각과 집계 기준일을 분리해 표시한다.
- 고객 화면에서는 업무 수정·삭제·권한 관리·세부 감사 로그를 노출하지 않는다.

### 디자인 규격

- 최대 폭 1280px의 중앙 정렬 12열 그리드, 카드 간격 16px.
- 배경은 아주 옅은 회색, 카드는 흰색, 기본 강조색은 포켓 진남색을 사용한다.
- 상태색은 정상 초록, 주의 주황, 위험 빨강 세 가지로만 사용한다.
- 상단 KPI 카드는 높이 88px 이내로 제한하고 큰 숫자와 짧은 비교 문구만 둔다.
- 추이는 복잡한 범례 대신 스파크라인과 전 기간 대비 수치만 보여준다.
- 고객용 모바일 화면은 KPI 2열, 나머지는 1열로 재배치한다.

## 5. 운영 관제

### 사용자가 답을 얻어야 하는 질문

1. 오늘 어느 프로젝트에 먼저 개입해야 하는가?
2. 지연·보류·고객 대기 원인은 무엇인가?
3. 누가 과부하이거나 담당이 비어 있는가?
4. 이번 주 마감과 승인 대기는 무엇인가?
5. KPI 하락이 업무 지연과 연결되는 프로젝트는 어디인가?

### 화면 구조

```text
[기간] [고객사/프로젝트] [담당] [상태]                       [새로고침 시각]

[지연] [보류] [3일 내 마감] [고객 대기] [KPI 위험]

[프로젝트 건강도 표 ------------------------------------] [결정 필요 큐]
[상태 / 프로젝트 / 진행률 / 지연 / 다음 마감 / 담당 / 갱신] [우선순위·원인·조치]

[담당자별 진행·지연 업무] [프로젝트별 KPI 위험] [최근 사람 작업]
```

### 프로젝트 건강도 판정 초안

- `위험`: 기한 초과 미완료 업무가 있거나, 차단 이슈가 열려 있거나, 핵심 KPI가 목표 대비 임계치 아래인 경우.
- `주의`: 3일 이내 마감 업무가 진행률 기준에 못 미치거나, 3일 이상 사람의 업데이트가 없는 경우.
- `정상`: 위험·주의 조건이 없고 다음 마감과 담당이 지정된 경우.
- `데이터 부족`: 시작·종료일, 담당, KPI 실제값 등 판정에 필요한 원장이 비어 있는 경우. 이를 정상으로 간주하지 않는다.

초기 버전에서는 이 규칙을 결정론적으로 계산하고 판정 근거를 함께 보여준다. 통계적 이상 탐지는 충분한 일별 실적 이력이 쌓인 뒤 추가한다.

### 상호작용

- 상단 빠른 필터는 `기간 / 프로젝트 / 담당 / 상태` 네 개만 상시 노출한다.
- 위험 카드나 표의 숫자를 누르면 해당 조건이 적용된 기존 업무 또는 성과 화면으로 이동한다.
- 결정 필요 큐에서는 담당 지정, 상태 변경, 고객 확인 요청 이동만 제공하고 복잡한 업무 편집은 상세 화면에서 한다.
- 최근 업데이트는 시스템 동기화 로그가 아니라 사람이 생성·수정·완료한 이벤트만 표시한다.

### 디자인 규격

- 데스크톱 전체 폭을 사용하되 좌측 메뉴를 제외한 본문은 최대 1600px로 제한한다.
- 상단 필터는 52px 높이의 고정 바, KPI 카드는 한 줄에 5개까지 표시한다.
- 건강도 표는 행 높이 44px, 첫 화면에서 최소 8개 프로젝트가 보이게 한다.
- 색만으로 상태를 구분하지 않고 `정상 / 주의 / 위험 / 데이터 부족` 문구와 원인을 함께 표시한다.
- 차트는 비교 판단에 필요한 담당자 부하와 KPI 위험에만 사용하고, 나머지는 정렬 가능한 표와 큐로 처리한다.

## 6. 권한과 메뉴

| 화면 | 포켓 | NS | 고객사 |
| --- | --- | --- | --- |
| 고객 브리핑 | 모든 접근 프로젝트 보기·미리보기 | 담당 프로젝트 보기 | 자기 프로젝트 읽기 |
| 운영 관제 | 전체 보기·조치 | 접근 프로젝트 보기·조치 | 접근 불가 |

- 권한 관리의 고객 페이지 선택지에는 `고객 브리핑`만 추가한다.
- `운영 관제`는 내부 역할 전용으로 고정해 고객 권한 체크박스에 노출하지 않는다.
- 기존 `총괄 현황`은 두 화면 검증 후 제거하거나 내부 기본 진입을 운영 관제로 교체한다.
- 기존 `#tasks/schedule` 링크는 `업무` 화면 내부 일정표로 계속 열리지만 좌측에는 별도 일정표 메뉴를 표시하지 않는다.

## 7. 데이터 구조

### 기존 원장에서 파생 가능한 값

- 프로젝트: 프로젝트명, 기간, 설명, 공개 상태.
- 업무: 상태, 진행률, 담당, 일정, 완료 링크, 변경 시각.
- 이슈·요청: 유형, 상태, 담당 주체, 마감.
- KPI: 정의, 목표, 실제값, 집계일, 데이터 출처.
- 활동 로그: 사람이 생성·수정·완료한 이벤트.

### 추가가 필요한 원장

- `project_status_updates`: 기간별 한줄 요약, 완료한 일, 현재 하는 일, 다음 일, 작성자, 작성 시각.
- 고객 확인 요청은 기존 이슈 원장으로 표현할 수 있으면 새 테이블을 만들지 않는다.
- 프로젝트 건강도는 초기에는 저장값이 아닌 조회 시 계산값으로 둔다. 필요할 때만 관리자의 수동 상태 덮어쓰기를 추가한다.

### 성능 원칙

- 화면에서 프로젝트별 API를 반복 호출하지 않는다.
- `read_client_brief(project_id, from, to)`와 `read_operations_dashboard(from, to, filters)` 두 개의 읽기 전용 집계 RPC로 카드·표·큐 데이터를 한 번에 받는다.
- 원장 행은 직접 복제하지 않고 집계 결과만 반환한다.
- 기간·프로젝트 필터 컬럼에 필요한 인덱스를 추가하고 실제 실행 계획으로 검증한다.
- 0과 미집계를 구분하도록 수치와 함께 `data_status` 및 `as_of`를 반환한다.

## 8. 구현 순서

1. `고객 브리핑` 정적 화면과 실제 프로젝트 데이터 매핑.
2. 프로젝트 상태 업데이트 원장과 저장 RPC 추가.
3. `운영 관제` 집계 RPC와 읽기 화면 구현.
4. 카드에서 기존 업무·성과 화면으로 이동하는 상세 필터 연결.
5. 포켓·NS·고객 계정별 권한 및 빈 데이터 상태 QA.
6. 두 화면 검증 후 기존 `총괄 현황`의 대체 또는 제거 결정.
7. 성과 데이터 원장 안정화 후 채널별 추이·이상 징후 모듈 추가.

## 9. 완료 기준

- 고객은 첫 화면에서 10초 안에 진행 상태, 최근 완료, 다음 일정, 본인 확인 요청을 파악할 수 있다.
- 내부 사용자는 위험 프로젝트와 개입 이유를 첫 화면에서 정렬해 볼 수 있다.
- 카드 숫자와 상세 화면의 필터 결과가 일치한다.
- 미연동·미집계 값이 0으로 표시되지 않는다.
- 고객은 다른 프로젝트, 운영 관제, 내부 메모, 세부 감사 로그에 접근할 수 없다.
- 첫 조회는 프로젝트별 연쇄 요청 없이 단일 집계 요청으로 완료된다.
