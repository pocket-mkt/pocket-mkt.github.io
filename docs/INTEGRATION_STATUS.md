# 운영 데이터 연동 현황

## 현재 결론

### 2026-09-07 프로젝트별 아이디 관리대장

- 프로젝트 메뉴 아래에 `아이디 관리대장`을 추가했다. Pocket/NS 내부 운영 계정만 보며, 현재 선택한 프로젝트의 활성 ADMIN/EDIT 멤버십 범위 안에서 사이트·주소·아이디·메모를 조회하고 등록·수정·삭제한다. 고객사 계정에는 메뉴와 권한 선택지를 모두 노출하지 않고 DB RPC도 거부한다.
- 비밀번호는 일반 업무 테이블에 평문으로 저장하지 않고 Supabase Vault secret으로 분리한다. 목록 RPC에는 평문과 Vault secret ID가 모두 없으며 `보기`를 누른 한 건만 별도 RPC로 복호화한다. 열람은 사용자·프로젝트·계정 식별자만 감사 로그에 남기고 비밀번호는 로그·세션스토리지·공용 리소스 캐시에 남기지 않는다.
- 등록·수정은 낙관적 row version과 mutation ID를 사용한다. 삭제는 대장 행을 보관 처리하면서 대응하는 Vault secret을 즉시 삭제하므로 해당 비밀번호는 화면에서 복구할 수 없다. Supabase Vault 백업은 암호화 상태로 포함된다.
- 대장 화면과 전용 CSS는 해당 메뉴에 처음 들어갈 때만 지연 로드한다. 초기 공용 번들에 비밀번호 관리 화면을 넣지 않아 기존 로그인·업무 첫 화면의 로딩 비용을 늘리지 않는다. 운영 DB에서 Vault 확장, 강제 RLS, raw authenticated grant 차단, anon RPC 차단, authenticated RPC 허용을 확인했고 전체 단위·계약 검사 234개와 PGlite 보안 회귀, 프로덕션 빌드 및 Sites 패키징을 통과했다.

### 2026-09-07 만료 완료 업무의 보류·간트 지연 구간

- 일정이 지난 업무는 기존대로 조회 시 자동 `DONE/100`으로 계산하되, 사용자가 상태를 `ON_HOLD`로 명시하면 만료 후에도 보류가 유지된다. 미착수·진행 등 다른 수동 상태는 만료 규칙을 우회하지 못한다.
- 간트는 보류 업무의 예정 종료일 다음 날부터 한국시간 오늘까지 어두운 회색 줄무늬 구간을 연장한다. 보류에서 완료로 돌아오면 `tasks.overdue_hold_resolved_at`을 저장하고 회색 구간을 그 날짜에서 고정한다. 보류 이력이 없는 일반 완료 업무에는 지연 구간을 그리지 않는다.
- 일정 또는 간트 날짜를 다시 편집하면 새 일정이 기준이 되므로 이전 보류 종료 기록을 비우고 자동 일정 모드로 복귀한다. 고객용 업무 투영에도 보류 종료 시각만 포함하며 실행 조직·내부 메모 마스킹은 유지한다.
- 운영 DB에는 `status_mode`와 `overdue_hold_resolved_at`, 상태 계산 함수·정규화 트리거·프로젝트 범위 읽기 투영을 적용했다. 기존 원격 migration history와 현재 파일명의 버전 체계가 달라 `db push`는 사용하지 않고, 검증된 단일 SQL을 Management API `db query`로 실행했다. 기존 만료 업무 15건의 저장 상태는 일괄 덮어쓰지 않았고 읽기 투영에서만 자동 완료를 계산한다.
- 프런트 상태/서울 날짜/보류 구간 테스트 57개, 전체 PGlite 마이그레이션·RLS·RPC·완료→보류→완료 회귀, 프로덕션 빌드를 통과했다. 운영 DB에서 만료 수동 보류는 `ON_HOLD`, 만료 수동 진행은 `DONE`, 신규 컬럼 각 1개를 확인했다. 기존 Advisor 경고 외 이번 변경에서 추가된 경고는 없다.

### 2026-09-04 업무 다중 이동·간트 축 추적·선택 일괄 삭제

- 일정표와 간트에서 체크한 여러 업무 중 하나의 이동 손잡이를 끌면 선택 업무 전체가 기존 상대 순서를 유지한 채 함께 이동한다. 대상 행의 위·아래 절반에 따라 남색 가상 삽입선과 `여기에 이동` 표시를 보여주고, 스크롤 영역 상·하단에 가까워지면 포인터를 유지한 채 자동 스크롤한다.
- 다른 매체 그룹으로 드롭하면 이동한 업무의 `category_code`를 대상 매체로 맞추고 전체 `sort_order`와 한 배치로 저장한다. 검색 또는 필터가 적용된 일부 목록에서는 원장 순서 훼손을 막기 위해 이동을 계속 비활성화한다.
- 체크박스는 마지막 선택 행을 기준으로 Shift 범위 선택·해제를 지원한다. 선택 툴바에 2단계 확인 방식의 `선택 삭제`를 추가했고 삭제는 `ARCHIVE` 배치로 처리해 업무 로그와 복구 가능한 원장 이력을 남긴다.
- 간트 날짜 셀에 포인터를 올리면 해당 업무 행과 같은 날짜 열 전체를 반투명 포켓 남색으로 강조하고 교차 셀에 진한 외곽선을 표시한다. 일정 칠하기를 시작하면 축 강조를 제거해 드래그 미리보기와 충돌하지 않는다.
- 단위·계약 검사 217개와 프로덕션 빌드를 통과했다. 기존 Supabase `mutate_tasks_batch`가 UPDATE와 ARCHIVE를 모두 원자적으로 처리하므로 신규 DB 스키마 변경은 없다.

### 2026-09-04 간트 업무명 가독성·날짜축 정리

- 간트 업무명 열은 현재 표시된 가장 긴 업무명과 체크박스·상태·담당·수정 버튼 폭을 합산해 360~620px 사이에서 자동 조정한다.
- 업무명 열을 제외한 화면의 남은 폭은 24px 날짜 열로 채운다. 마지막 실제 일정이 9월에 끝나고 공간이 남으면 10월 날짜까지 자연스럽게 이어 표시한다.
- `ResizeObserver`로 컨테이너 폭이 바뀔 때 업무명·날짜 영역을 다시 계산하되 저장 데이터는 변경하지 않는다.

### 2026-09-04 업무 추가 필수 입력 해제

- 업무 추가·완료 업무 추가에서 업무명 필수 표시와 저장 버튼 잠금을 제거했다. 업무 분야·담당·상태는 기존 기본값이 선택된 상태라 별도 확인 클릭 없이 바로 저장할 수 있다.
- 업무명을 비워 저장하면 DB 제약과 로그 식별성을 깨지 않도록 `제목 없는 업무`로 정규화한다. 잘못된 날짜 범위·0~100 밖 진행률·HTTPS가 아닌 완료 링크처럼 데이터 자체가 유효하지 않은 입력 검사는 유지한다.

### 2026-09-04 고객사 계정 모달·프로젝트 하위 권한 분리

- 고객사 계정 생성·편집 모달은 960px 폭의 단일 폼으로 바꾸고, 계정 필드만 2열로 정렬했다. 기존에는 760px 모달 안에서 전역 2열 폼과 내부 2열 그리드가 중첩돼 각 영역이 절반 폭으로 눌리고 문구가 어긋났다.
- 접근 페이지 선택을 `기본 메뉴`와 `프로젝트` 두 영역으로 나눴다. 프로젝트 영역의 `업무 / 진행상황 / 데일리 회의록`은 각각 독립적으로 선택·저장·메뉴 노출을 제어한다.
- `progress`를 프런트, Apps Script, Supabase Auth 브리지, access-admin 허용 목록 및 DB 제약에 정식 페이지 코드로 추가했다. 진행상황 전용 권한은 업무 메뉴를 열지 않지만, 진행상황 렌더링에 필요한 고객 공개 업무 투영만 읽을 수 있다. 고객 계정은 계속 `READ_ONLY`라 업무 쓰기 권한은 생기지 않는다.
- 기존 `schedule`은 독립 메뉴가 아니라 `tasks` 내부 화면으로 유지한다. 단위·계약 검사 209개를 통과했다.

### 2026-09-04 업무 이동 발견성·일정표 세로 정렬

- 기존 업무 이동은 필터가 모두 해제된 상태에서 작은 점 손잡이를 끄는 방식이라 기능이 보이지 않았고, 접힌 회차 묶음은 이동할 수 없었다. 일정표 손잡이에 `이동` 문자를 표시하고 화면 설명을 추가했으며, 간트 손잡이와 동일한 저장 경로를 유지한다.
- 개별 업무뿐 아니라 접힌 번호 회차 묶음도 손잡이 하나로 통째로 이동한다. 묶음 내부 순서와 개별 DB 행은 유지하고, 이동 결과만 기존 `sort_order` 일괄 mutation으로 저장한다. 필터·검색 중에는 일부 목록 기준으로 원장 순서가 훼손되지 않도록 계속 비활성화한다.
- 일정표 본문 셀의 상단 정렬을 제거하고 셀 컨테이너를 세로 중앙 정렬했다. 매체·업무분야·업무·세부내용·일정·기간·진행률·상태·담당·링크·비고·관리 열에 동일하게 적용하며, 두 줄 세부내용도 다른 열의 중심선과 맞춘다.
- 단위·계약 검사 198개와 격리 Chromium에서 다중 행의 모든 셀 중심 오차 1.1px 이하, 1100/1440/1920px 열 너비, 날짜 편집, 번호 회차 접기·펼치기를 검증했다.

### 2026-09-04 번호 회차 업무 접기

- `콘텐츠 제작 / 업로드 1/10`처럼 제목 끝의 `현재회차/전체회차`만 다른 업무는 매체·업무분야·기본 업무명이 같을 때 일정표와 간트에서 한 개의 묶음 행으로 표시한다. 기본은 접힌 상태이며 `>`를 누르면 원본 회차 행이 펼쳐진다.
- 접힌 행은 전체 일정 범위, 평균 진행률, 상태별 개수, 공통 담당과 등록된 링크 수를 요약한다. 간트는 여러 회차의 일정 합집합을 줄무늬 막대로 보여주고, 잘못된 대량 일정 수정을 막기 위해 펼친 개별 행에서만 날짜를 칠하거나 지울 수 있다.
- 업무 원장은 합치지 않는다. 각 회차의 날짜·진행률·상태·담당·링크와 변경 로그는 기존 개별 DB 행으로 유지하고, 묶음 체크박스는 해당 회차 전부를 기존 일괄 변경 경로로 선택한다. 필터 결과가 한 건만 남으면 묶지 않는다.
- 단위·계약 검사 197개와 격리 Chromium에서 기본 접힘, 일정표 펼침, 간트 상태 공유, 다시 접기, 기존 날짜 편집·필터·반응형 화면을 검증했다.

### 2026-09-04 업무 자동 상태·일괄 변경·순서 편집

- 일정표와 간트의 상태·담당을 순환 클릭에서 명시적 드롭다운으로 통일했다. 상태는 미착수/진행/완료/보류, 담당은 포켓/NS/해당 고객사 중 직접 선택하며 기존 권한·낙관적 저장·오류 롤백 경로를 그대로 사용한다.
- 시작일 전은 미착수, 시작일부터 종료일까지는 진행, 종료일 다음 날부터는 예외 없이 완료·100%로 계산한다. 사용자가 기간 중 상태만 바꾸면 수동 상태를 유지하지만 날짜 또는 간트 일정이 바뀌면 자동 모드로 돌아간다. 만료 판정은 수동 상태보다 우선한다.
- 이 규칙은 브라우저 표시뿐 아니라 `tasks.status_mode`와 공통 DB 트리거·읽기 RPC에 적용한다. 적용 시점에 이미 만료된 활성 업무는 실제 원장도 완료·100%로 한 번 보정하고, 이후 날짜가 자정을 넘기면 다음 조회에서 한국 날짜 기준 최신 상태를 반환한다. 시스템 보정은 행위자가 없는 감사기록으로 남겨 사람의 업무 로그에는 표시하지 않는다.
- 일정표와 간트에 행 체크박스와 현재 표시 행 전체선택을 추가했다. 선택 업무의 상태·담당을 한 번에 바꾸며 40건 단위 배치 mutation으로 저장한다. 필터·검색은 로컬 표시만 바꾸고 선택 업무 원장은 동일하다.
- 검색과 필터가 없는 전체 목록에서 드래그 손잡이로 업무 순서를 바꾸고 `sort_order`를 저장한다. 두 화면 모두 매체별로 묶은 뒤 저장 순서를 따르며, YouTube는 본편 회차와 같은 회차의 조회수·좋아요·댓글 작업을 붙이고 쇼츠 묶음은 뒤에 둔다.
- 프런트 자동 상태·서울 날짜 경계·YouTube 묶음 정렬·체크/일괄/드래그/드롭다운 계약 테스트 44개, 전체 193개 검사, Supabase migration/RLS/RPC/감사 회귀와 실제 Chromium 일정표·간트 검사를 통과했다. 프런트는 커밋 `1cff918`로 GitHub Pages 배포가 완료됐다. 운영 Supabase migration은 MCP OAuth refresh 응답 파싱 오류로 아직 적용하지 않았으며, 그 전까지 프런트는 `status_mode`가 없는 기존 행을 수동 상태로 취급해 날짜만으로 상태를 덮어쓰지 않는다.

## 원장에 준비된 범위

원장은 다음 관계를 불변 ID로 연결하도록 설계돼 있습니다.

`고객사 → 프로젝트 → 업무·콘텐츠 → 승인·성과 → 파일·활동로그`

승인된 UND 업무 144건은 운영 집계에 포함됩니다. 기존 103건에서 144건으로 이관할 때 의미상 동일 업무는 상태·담당자·메모를 보존하고 누락 업무만 추가하도록 마이그레이션을 구성했습니다. 콘텐츠, 승인, 성과, KPI 실적은 운영 입력을 받는 원장입니다. 외부 채널 API는 아직 연결되지 않았습니다.

업무 144건의 구성은 다음과 같습니다.

| 구분 | 건수 |
|---|---:|
| P0 / M1 / M2 / M3 | 57 / 31 / 28 / 28 |
| 마케팅 / 디자인 / 영상 | 79 / 35 / 30 |

업무 API는 프로젝트 `start_date`, 업무 `plan_week`, 명시적인 `planned_start_date`·`due_date`를 반환합니다. UND 144건과 무극 20건은 모두 두 날짜를 저장하며, 프런트의 계산 경로는 구버전 무일정 행을 위한 호환용입니다. `plan_note`는 내부 상세에서만 조회되며 고객 화면은 `description`, `contract_linked` 여부와 공개 진행 메모를 확인합니다.

세부 탭과 필드 정의는 [데이터 모델](DATA_MODEL.md), 화면별 읽기 구조는 [API 계약](API_CONTRACT.md)을 기준으로 합니다.

## 공개 범위

원장과 API 공개 범위는 `POCKET_ONLY`, `PROJECT_TEAM`, `CLIENT`로 통일했습니다. 기존 `INTERNAL` 값은 `POCKET_ONLY`로 이관했고, 신규 실행사 입력의 기본 공개 범위는 `PROJECT_TEAM`입니다.

권장 기준은 다음 세 단계입니다.

| 코드 | 공개 대상 | 포함 예시 |
|---|---|---|
| `POCKET_ONLY` | 포켓 내부 | 전략, 원가, 위험, 계약 기준, 내부 메모 |
| `PROJECT_TEAM` | 포켓 + 배정 실행사 | 제작 지시, 작업 메모, 실행사 담당 정보 |
| `CLIENT` | 고객사 | 일정, 공개 결과물, 승인 요청, 공개 성과 |

고객 공개는 포켓 검수 후 `CLIENT`로 변경합니다.

## 운영 구조

```text
GitHub Pages 프런트엔드
        ↓ HTTPS
Apps Script API
        ├─ 로그인 세션 확인
        ├─ 사용자·프로젝트 권한 확인
        ├─ 역할별 응답 필드 화이트리스트
        ├─ 입력 검증·동시 저장 제어
        └─ 활동로그 기록
        ↓
비공개 Google Sheets 원장
```

브라우저가 보낸 `role`, `client_id`, `project_id`는 권한 근거로 신뢰하지 않습니다. 서버가 로그인 사용자와 프로젝트 권한표를 기준으로 접근 범위를 다시 계산해야 합니다. 시트 원본은 비공개로 유지하고 고객에게 직접 공유하지 않습니다.

- 행은 기본 `CLIENT` 공개 범위입니다. 업무 페이지를 볼 수 있는 고객 계정은 읽기만 가능하고 포켓·NS 편집 계정만 쓸 수 있습니다. 원시 테이블의 브라우저 권한은 0건이며 RLS 3개 정책과 제한된 RPC만 노출합니다.
- 원격 DB에서 생성 → 조회 → 수정 → 보관을 한 트랜잭션으로 실행한 뒤 롤백하는 검증을 통과했습니다. 로컬 보안 QA는 23개 공개 테이블 전부 RLS, 미색인 FK 0건, 이슈 URL 거부·낙관적 동시성·보관 제외를 확인합니다.
